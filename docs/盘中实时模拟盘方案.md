# 盘中实时模拟盘方案（顿悟股道 × 实时 L2 闭环）

> 文档定位：在现有 `replay-backend`（盘后复盘 S1–S8）基础上，扩展出一套**盘前定方向 → 盘中 L2 实时决策 → 盘后结算 → 经验反哺**的模拟盘闭环。
> 本文是**设计文档 + 表结构契约**，不动手写业务代码（表结构先行，代码后落）。
> 关键定位：本系统同时是未来**量化 agent 系统的数据底座**——所有模拟成交与经验反馈都以可被 agent 训练消费的可查询 schema 落库。

---

## 0. 设计原则（先立规矩）

1. **源无关（Source-agnostic）**：后端只接收 JSON 行情流，不关心 L2 来自同花顺 / 通达信 / 东财。换提供商只改 Python producer，后端零改动。
2. **传输与计算分离**（用户明确要求的标注）：
   - **Redis Streams = 仅传输 / 缓冲 / 解耦 / 可重放**（爬虫生产、后端消费之间的管道）；
   - **计算逻辑 = 后端自写内存滚动窗口**（大单净主动买入、封单、炸板回封），**不引入 Flink / Spark**。
3. **多口径统计优先**：每一笔模拟成交都带 `strategy_id × stage(入场情绪阶段) × capital_confirm(资金层口径) × direction × role`，后期按这些维度 GROUP BY 算胜率/盈亏，**由数据收窄策略**，而非预先写死"只做某阶段"。
4. **战法全量注册 + 资金层正交**：把《顿悟股道》所有买入战法都注册成策略；资金流（L2 大单）只是一层**可开关的正交信号**（过滤/确认/忽略），不砍掉其他战法。
5. **模拟盘优先于实盘**：全程模拟成交、每步留决策建议，攒样本；真实交易由人执行。
6. **一致性约定沿用现有工程**：CK 业务/分析表沿用 `ReplacingMergeTree` + `_ver DateTime MATERIALIZED now()` + 纯 INSERT 幂等；实时热数据走 Redis。金额=元、幅度=%、成交量=手。

## 1. 整体闭环架构（7 模块）

```
┌─ T-1 盘后（复用 S1–S8 复盘） ────────────────────────┐
│ ① 盘前计划 plan_pool                                  │
│    三重共振(大势S1+情绪S2+寻龙S4) → 方向+股票+候选战法  │
│    + 触发价/计划仓位/计划动作                          │
│    （对应需求 4.1：基于综合研判给明天关注目标）         │
└───────────────────────┬─────────────────────────────┘
                        │ 用户确认/调整 → 放入关注池
┌─ T 日 盘中（新模块） ──▼─────────────────────────────┐
│ ② 实时接入 ingest：Python爬虫→Redis Stream→后端        │
│    （用户负责：同花顺L2 hexin-v 主源 + pytdx/东财 备源）│
│ ③ 流式计算 stream：内存滚动窗口 → realtime_feature      │
│    （大单净主动买入 / 封单 / 炸板回封 / 放量突破）       │
│ ④ 交易元决策引擎 trader：                              │
│    战法注册表(全量) + 资金层正交信号                   │
│    → 决策建议 action/score/reason/参考价               │
│ ⑤ 模拟盘 sim：按建议+计划仓位模拟成交（每步决策建议）   │
│ ⑥ 前端 SSE 推送（非 WebSocket）：盘中监控 + 决策流 + 模拟盘    │
│    （对应需求 4.2：实时回传+资金确认+按计划模拟买入）    │
└───────────────────────┬─────────────────────────────┘
                        │ T 收盘
┌─ T 盘后（新模块） ─────▼─────────────────────────────┐
│ ⑦ 结算：sim_account/position 算当日收益 → 生成次日卖出 │
│    计划（对应需求 4.3）；并触发 rt_* 每日归档到 CK(回测源头)│
│ ⑧ 经验反馈 exp_log：每笔模拟单+当时L2特征+结果         │
│    → 反哺两个智能体（对应需求 4.4）：                   │
│      · 市场分析师 = 复盘系统(S1–S8) 调参               │
│      · 交易元 = L2 决策 学"哪些真哪些骗"               │
│    （对应需求：数据底座 → 未来量化 agent 消费）          │
└──────────────────────────────────────────────────────┘
```

诚实边界：盘中只能**推断大单**（金额阈值+方向），不能**确认席位身份**（席位仅 T+1 龙虎榜）。故盘中抓"行为痕迹"，盘后龙虎榜"验明正身"——两者互补。

## 2. 数据来源与接入契约（L2，源无关）

### 2.1 用户侧负责（本方案不越权）

- **主源**：同花顺 L2（已付费）。`hexin-v` token 由 Node+jsdom 生成、Python 子进程调用、401 自动刷新——**可行**，唯一软肋是 chameleon JS 改版会崩。
- **备源（建议补充，非必须）**：`pytdx`（通达信直连，免费稳定，分笔带 `buyorsell` 方向：0 买/1 卖/2 中性，L1 约 3 秒切片）/ 东财 `push2`（无 token 体操，提供逐笔方向）。token 一崩，管道不至于全断。
- **优先"推"优于"轮询"**：能接推送通道就别高频轮询，延迟更低。

### 2.2 后端接入契约（producer 推来的 JSON，后端只认这个）

爬虫抓取并推送以下三类消息（topic 用 Redis Stream key 区分）：

| 类别 | Stream Key | 字段 | 用途 |
|---|---|---|---|
| 逐笔成交 tick | `rt:tick` | `ts_code, ts(毫秒), price, volume(手), amount(元), direction(0买/1卖/2中性)` | 大单净主动买入、对倒识别 |
| 盘口/行情快照 | `rt:quote` | `ts_code, ts, last_price, pct_chg, amount_day, turnover, high, low, limit_up_price, bid1~10(price,vol), ask1~10(price,vol), seal_amount(封单额)` | 封单变化、炸板回封、扫单 |
| 板块/指数实时 | `rt:sector` | `board_code, ts, pct_chg, lead_ts_code` | 用户提到"板块也可传回"，供板块级共振 |

> 接口层约定：后端消费 Redis Stream，按 `ts_code` 分桶维护内存滚动窗口；崩溃后从 Stream `last-delivered-id` 重放，数据不丢。

### 2.3 中间件标注（显式区分，避免混淆）

- **Redis Streams = 唯一传输总线（全阶段，含 MVP）**：传输 / 缓冲 / **彻底解耦** / 可重放。爬虫只管生产到 Stream，后端 consumer group 消费，二者互不依赖；爬虫崩溃/重启可从 `last-delivered-id` 重放，数据不丢。**WebSocket 直推被否决**（生产/消费强耦合、爬虫崩即丢数据、难重放、难扩展，违背"必须解耦"）。
- **Kafka**：未来扩到全市场/多用户时再上，当前几十只票属 overkill。
- **计算引擎 = 后端自写内存滚动窗口**：每个 `ts_code` 一个 RingBuffer，算近 1/5/15 分钟大单净主动买入额、封单、炸板回封事件。不引入 Flink/Spark Streaming。
- **前端实时展示不用 WebSocket**：后端→前端改用 **SSE（Server-Sent Events）** 单向推送（或短轮询）。后端把 Redis Stream 的消费结果经内存事件总线转发给 SSE 端点，前端与采集链路完全解耦，且不引入 WS。

### 2.4 延迟预算

同花顺 L2 本身 ~1–3s + 抓取周期 + 推送 + 计算 ≈ **秒级滞后**（可达目标，但模拟器抓取有抖动，别追求零延迟）。

## 4. 表结构设计（核心 · 数据底座）

> 约定：CK 业务/分析表用 `ReplacingMergeTree`，`ORDER BY` 见各表；`_ver DateTime MATERIALIZED now()` 省略标注。
> 实时热数据（tick/quote/feature）**Redis 仅作盘中热缓存**，必须**每日收盘后持久化到 CK 归档层**（plain MergeTree，不可变 append，无需 FINAL）——作为历史回测可溯源的"源头 tape"，Redis 不能长期留存。
> 维度字段（stage / capital_confirm / direction / role / action）一律用**枚举/短码**而非自由文本，保证可 GROUP BY 统计。

### 4.2.4 每日持久化到 CK（历史回测源头）★

> 需求：Redis 仅作盘中热缓存、不能长期留存；为支持**历史回测找源头**（任意一笔模拟成交/决策都能回溯当时真实 L2 逐笔），盘中热数据必须在**每日收盘后持久化到 CK 归档层**，作为不可篡改的"源头 tape"。

- **持久化时机**：盘后结算（⑦）之前由 `RtArchiveService` 触发。tick 采用 **dual-write**（盘中每笔异步直写 CK 归档，零丢失保证）；feature 本就 CK RMT 连续写入无需额外批处理；收盘后统一 `XTRIM` 清理 Redis Streams。
- **写入方式**：复用现有 `CkHttpWriter`（裸 HTTP 批量直写，异步、幂等）；tick 用 plain MergeTree（不可变 append，无需 FINAL）。
- **归档表**（CK，plain MergeTree，按 `trade_date` 分区）：
  - **`rt_tick_archive`（★真实源头）**：`trade_date Date, ts_code String, ts DateTime64(3), price Float64, volume Float64, amount Float64, direction Enum8`；ORDER BY (ts_code, ts)。承接 Redis `rt:tick` 全量逐笔。
  - **`rt_quote_archive`（盘口降采样）**：结构同 `realtime_quote` + `trade_date`，但**仅按固定间隔（每 5–10s）或事件（炸板/回封）落盘**，避免全量快照撑爆 CK；Redis 仍为盘中完整热数据。
  - `realtime_feature` 已在 4.2.3 连续落 CK RMT，作为派生特征源头。
- **回测关联（核心价值）**：`sim_trade` / `decision_log` 携带 `(ts_code, trade_time)`，可直接 `JOIN rt_tick_archive` 重建触发该笔决策的完整逐笔 tape；`exp_log.entry_features_json` 亦可由 archive 回填校验。**即每一笔模拟交易都可审计、可重放、可归因**。
- **Redis 生命周期**：Streams 保留 ≥1 个交易日（防当日崩溃重放），归档完成后 `XTRIM` 至上限；热 hash（`rt:quote`）设 TTL 或收盘清理。

> **多口径统计 SQL 范式**（后期收窄策略用）：
> ```sql
> SELECT strategy_id, stage_at_entry, capital_confirm,
>        count() AS n,
>        sum(pnl>0 ? 1 : 0)/count() AS win_rate,
>        avg(pnl) AS avg_pnl
> FROM sim_trade FINAL
> WHERE side='SELL' AND pnl IS NOT NULL
> GROUP BY strategy_id, stage_at_entry, capital_confirm
> ORDER BY win_rate DESC, n DESC;
> ```
> 由此得到"哪种 (战法 × 阶段 × 资金口径) 组合挣钱最大"，再把低胜率组合在 `strategy_catalog` 置 `enabled=0` 或调 `capital_role`。

## 5. 交易元决策引擎（④ 多战法 + 资金正交信号）

1. **战法注册表**：启动时从 `strategy_catalog` 载入全部 `enabled=1` 战法，每个带 `applicable_stages` + `board_pos` + `capital_role` 元数据。
2. **盘中匹配**：每收到 `realtime_feature`，结合当日 `stage_snapshot` + 标的 `role` + `plan_pool` 候选战法，筛出**当前适用的战法集合**。
3. **资金层正交处理**（按 `capital_role`）：
   - `IGNORE`：资金层不参与；
   - `FILTER`：大单净卖/CONTRA 时否决买入；
   - `CONFIRM`：必须有大单净主动买入才确认信号。
4. **决策输出**：`action(BUY/SELL/HOLD/WATCH) + score(0–100) + risk_level + reference_price + reason + strategy_id + stage + capital_signal`，写入 `decision_log` 并 WS 推送。
5. **模拟盘执行**：`sim_order`/`sim_trade` 按决策 + `plan_pool.planned_position_pct` 模拟成交，每步带 `strategy_id/stage_at_entry/capital_confirm` ★。

### 11.2 d1/d5 收益口径

```
d1_ret = (close(T+1) - basis_price) / basis_price × 100
d5_ret = (close(T+5) - basis_price) / basis_price × 100
```
- **basis_price 统一取「买入价」**（关键修正，见 11.7）：sim_trade 的 d1_ret/d5_ret 对 BUY/SELL 笔均回填"买入后持有不动"基准；exp_log 闭环经验也用配对 BUY 笔的买入价算。
  语义=「如果当初买入死拿，到 T+1/T+5 赚多少」——与主动买卖 pnl 横向对比才有意义，且**卖出当天 T+1 尚无数据时用 BUY 基准可立即带值，不必等后续交易日补齐**。
- 数据源：`stock_daily` 真实收盘价（TreeMap 取晚于成交日的第 N 个交易日，自然日升序近似交易日）。
- 回填方式：RMT 重 INSERT 整行（ORDER BY trade_id + _ver 折叠），不 UPDATE。
- T+N 无数据（超出 stock_daily 已有范围）→ d1/d5 留 NULL，正确跳过。

### 11.3 exp_log 生成口径

- 以「卖出闭环 / 买入开仓」为单位配对 BUY→SELL（按 ts_code 升序，openBuy 游标配对）。
- 闭环经验：回溯同 ts_code 最近一笔 BUY 的 entry 信息；开仓经验（仍持仓）：direction=BUY，outcome_pnl=NULL。
- 多口径维度齐备：`strategy_id × stage × capital_confirm × direction × role`。
- `exp_id = "EXP_" + trade_id` → **幂等**（重跑不产生重复经验，已验证：启动 recalc + 手动 settle 两次触发，exp_log 仅 1 条）。

### 11.4 XTRIM 语义

- 盘中 L2 tick 已双写 `rt_tick_archive`（CK 持久化），stream 仅作传输总线，不需保留历史。
- `maxLen` 默认 1000（≈1 小时窗口兜底），收盘 cron `0 5 15 * * ?` 自动裁；手动 `POST /admin/xtrim` 即时裁。
- 验证：rt:tick 1465 条 → xtrim → 1000 条（阈值裁剪生效）。

### 11.5 端到端验证结论（本地 Redis + Windows CK）

- **d1/d5 回填**：造 8-18 BUY + 8-21 SELL（000069.SZ），BUY 笔算出 `d1_ret=-0.565%`（8-19 收盘 1.76 vs 买价 1.77，正确）；SELL 笔 T+1=8-22 尚未产生 → NULL（正确行为）。
- **exp_log 生成**：闭环经验 1 条，多口径维度齐全，lesson 正确（"闭环亏损 0 元：需复盘卖出时机"）。
- **幂等**：exp_log 重跑不重复（FINAL count=1）。
- **XTRIM**：1465→1000 按阈值裁剪生效。
- 启动 `calc.on-startup=true` 时 M2 结算自动挂在 recalc 末尾执行（日志：`盘后结算开始/结束: 2026-08-21`）。

### 11.7 设计瑕疵修复（2026-08-22）：SELL 闭环经验 d1/d5 口径

- **原缺陷**：exp_log 闭环经验的 d1/d5 取 SELL 笔自身价（"卖出后持有"基准），且依赖 SELL 笔 d1_ret 回填——SELL 当天 T+1 无数据 → 落 0。卖出当天的经验无法立即带 d1/d5。
- **修复**：`AfterCloseSettlement.buildExp` 对 SELL 闭环经验统一改用配对 BUY 笔的买入价 + 买入日算 T+N 基准（"买入后持有"基准）。BUY 开仓经验维持自身买价。
- **验证**：造 8-18 BUY + 8-21 SELL，修复后 SELL 经验 `d1_ret=-0.565%`（用买价 1.77，T+1=8-19 收 1.76）；旧逻辑落 0。幂等仍成立（`EXP_`+trade_id 派生，重跑不重复）。
- coding：`buildExp` 新增 basisRow 分支（isClosed→entryBuy，否则 closeOrOpen），closeAtOffset 用 basisDate 计算；类注释口径同步更新。

## 12. 同花顺 L2 Redis 契约对齐（2026-08-23）

用户给出「同花顺 L2 Redis 数据契约 v1.0」，与 M1 的「三全局流」范式**不兼容**（每股票一个 Stream + Hash 盘口 + Pub/Sub），后端消费层做了重写对齐。

### 12.1 契约 vs 后端模型差异
| 维度 | M1 旧 | 同花顺实测（REDIS_DATA_FORMAT.md，pcap 重放） |

| Stream 组织 | 3 全局流 `rt:tick/rt:quote/rt:sector` | 每股票流 `ths:l2:tick:{code}`；盘口是 **Hash** `ths:l2:quote:{code}`（非 Stream） |
| tick 字段 | `tsCode/ts/price/volume/amount/direction` | `t`(当日相对毫秒,从0点起算)/`p`(**恒0, JiTu无价**)/`v`(**恒0, 未解析量**)/`d`(B/S)/`a`(恒0) |
| quote 结构 | Stream payload | **Hash**：`code/tb10_prices(逗号分隔价格列表)/tb10_volumes/tb10_strings/tb10_count/tb10_data_len/timestamp(相对ms)/update_time` |
| 板块 | `rt:sector` 流 | 无板块流（仅 `ths:l2:pool` Set + `ths:l2:events` 心跳） |
| 发现机制 | 固定 3 流 | `SMEMBERS ths:l2:pool` + 订阅 `ths:l2:pool:change`（Pub/Sub）动态增删 |

### 12.2 后端改造（已编译通过 ✅）
1. **Tick POJO**（`model/Tick.java`）：`direction` 改 `String`，加 `DirectionDeserializer` 统一 B/S/0/1/2 → BUY/SELL/NEUTRAL；`ts` 加 `TickTimeDeserializer` 兼容 unix-ms 与当日相对毫秒；字段加 `@JsonProperty` 映射 `t/p/v/a`。`FeatureCalculator` 改用 `t.directionSign()`。JiTu 下 p/v/a 恒 0 是**预期**而非解析失败，Javadoc 明确标注；加 `isPriceMissing()` 供回贴判断。
2. **Quote POJO**（`model/Quote.java`）：双模式兼容——① 朴素模式：`tb10_prices/tb10_volumes` 原始串 + `parseTb10()` 拆列表按常量 index（`TB10_LAST_IDX=0 最新价 / BID1_IDX=1 / ASK1_IDX=2 / BID1V_IDX=3 / ASK1V_IDX=4`，待行情软件确认）；② 拆分模式：爬虫若直接给 `last_price/bid1_p/bid1_v/ask1_p/ask1_v` 则直接映射，`parseTb10` 不覆盖已填字段。
3. **RedisStreamConsumer**（`realtime/RedisStreamConsumer.java`）：**彻底重写消费模型**——tick 是 Stream（XREADGROUP + ACK）；**quote 是 Hash，改为 `HGETALL` 周期轮询**（默认每 1000ms，配置 `quote-refresh-ms`），转 JSON 复用 Quote `@JsonProperty` 映射 + `parseTb10()`，存入 `quoteCache` 并 `window.putQuote`。tick 入窗口前用该 code 最新 quote 的 `lastPrice` **回贴价格**（`isPriceMissing()` 为真且 quote 有价时）。订阅 `ths:l2:pool:change` 动态增删；30s 兜底刷新池。
4. **StreamTrimmer**：遍历 `ths:l2:pool` 对所有 `ths:l2:tick:{code}` 逐键 XTRIM（maxLen 10000 对齐契约）。
5. **application.yml**：redis host 默认 `100.97.74.45`；stream 段加 `pool-refresh-ms:30000`、`quote-refresh-ms:1000`、`xtrim-max-len:10000`。

### 12.3 关键约定（需爬虫侧遵守）
- **quote 是 Hash，不是 Stream**：后端已改为 `HGETALL` 轮询，爬虫**无需**额外 `XADD` quote Stream（旧"双写"约定作废）。直接 `HSET ths:l2:quote:{code} tb10_prices ... tb10_volumes ...` 即可。
- **tick 价格/量缺失是 JiTu 现状**：price 由后端从 quote 回贴；volume/amount 当前为 0，等爬虫逆向补量后自动生效（无需改后端）。**暂不可用**依赖量的特征（M3 拆单/对敲已做降级）。
- **tb10_prices 的 index 顺序待确认**：当前约定 `[最新价,买一,卖一,买一量,卖一量,...]`，爬虫对照行情软件确认后只需改 `Quote.java` 的 `TB10_*_IDX` 常量。
- **tick 时间格式**：`t` 是**当日相对毫秒**（如 605000=10:05:00.000），非 epoch。后端 `TickTimeDeserializer` 兼容两种；正式运行建议用相对毫秒（与快照 `timestamp` 同源）。
- **股票池**：爬虫 `SADD ths:l2:pool {code}` 维护订阅池，变更时 `PUBLISH ths:l2:pool:change '{"action":"add|remove","code":"xxx"}'`。

### 12.6 M3 拆单识别（2026-08-23 14:xx）
- **目标**：从逐笔 tick 流识别主力三类手法——拆单吸筹(STEALTH)、扫单(SWEEP)、对敲(SELF_TRADE)。
- **落点**：新增独立类 `OrderPatternAnalyzer.analyze(...) → Result(stealthNetBuy, sweepDensity, selfTradeRatio, orderPattern)`；`RealtimeFeature` 加 4 字段；`FeatureCalculator` 每 3s 调用注入；CK `realtime_feature` 表加 4 列。
- **算法要点**：
  - **拆单吸筹**：stealth 窗口(30s)内同向主买小单累计破万手 → 命中。
  - **扫单**：sweep 窗口(10s)内**价格上行因子主导**（priceFactor=min(1,涨幅×40)；价格平稳→强制 sweepDensity=0，避免与拆单混淆）+ 主买占比/量强度辅助。
  - **对敲**：±200ms 内量差≤15% 且反向成对笔 / 总笔数 → ratio。
- **⚠️ JiTu 量退化分支（2026-08-23 15:xx 加）**：`analyze` 开头探测 `hasVolume`（窗口内是否有 tick.volume>0）。量全缺时：拆单/对敲直接降级 `NORMAL`（不产出假信号）；扫单退化为纯价格上行因子（volStrength=0，仅价格驱动）。爬虫补量后 `hasVolume=true` 全部分支自动恢复。
- **验证**：`scripts/verify_m3_order_pattern.java` 覆盖 5 类（STEALTH/SWEEP/SELF_TRADE/NORMAL/**JITU_DEGRADED量全0→NORMAL**）全部 PASS。`mvn -o clean package` 通过。
- **注意**：离线仓库无 `spring-boot-starter-test`，验证以独立脚本固化在 `scripts/`。
- **待办**：① 真实 L2 数据跑通后校准阈值；② 拆单特征接资金三态/新增 S9_STEALTH_ABSORB 战法（M3+）；③ 前端实时页加 orderPattern 展示。

### 12.7 消费端容错降级骨架落地（2026-08-23 15:xx）
- **背景**：`REDIS_DATA_FORMAT.md` 实测揭示 JiTu 逐笔**无价无量**（p/v/a 恒 0）、quote 是 **Hash 非 Stream**，彻底推翻此前"tick 含 p/v/a、quote 是 Stream"的假设。原 `RedisStreamConsumer` 把 quote 当 Stream 读会直接抛异常/永远读不到。
- **改动清单**：
  1. `RedisStreamConsumer`：tick 仍 XREADGROUP（Stream）；**quote 改为 `HGETALL` 周期轮询**（默认 1000ms），Hash→JSON 复用 Quote 映射 + `parseTb10()`。
  2. **价格回贴**：tick 入窗口前用 `quoteCache` 最新 `lastPrice` 填补 `tick.price`（JiTu 无价）；量/金额缺失保持 0（不报错）。
  3. `Quote.java`：加 `tb10Prices/tb10Volumes/tb10Strings/tb10Count/tb10DataLen` 原始字段 + `parseTb10()` 解析（按 `TB10_*_IDX` 常量回填语义字段）；保留拆分模式字段映射（爬虫若给语义字段直接可用）。
  4. `OrderPatternAnalyzer`：加 `hasVolume` 探测与量退化分支（量全 0 时不误判拆单/对敲，扫单退化为纯价格驱动）。
  5. `verify_m3_order_pattern.java`：新增 `JITU_DEGRADED` 场景（量全 0 → 必须 NORMAL，不产假信号）。
- **效果**：爬虫侧只要按 Hash 写 `ths:l2:quote:{code}`（含 `tb10_prices`）+ Stream 写 `ths:l2:tick:{code}`（含 `t/d`），后端即可直接跑起来，无需等字段完全对齐再返工；量/十档补齐后特征自动增强。
