## 1. 起源：《顿悟股道》方法论与 8 skill 体系

《顿悟股道》是一套 A 股短线投机框架，核心思想可概括为「主线思维 + 龙头思维 + 主力博弈 + 情绪周期 + 趋势跟随 + 交易心法」。
产品化时把它拆成 **8 个可计算的 skill（S1~S8）**，每个 skill 对应书中的一个分析维度，由后端每日跑数产出结构化指标，再由前端可视化。

| Skill | 名称 | 书中断章 | 核心问题 | 计算层产出表 |
|------|------|---------|---------|------------|
| S1 | 大势择时 | 第一章 大势 | 现在处在牛熊周期哪一阶段、该不该出手 | `four_dimension_daily` |
| S2 | 情绪温度 | 情绪周期 | 市场赚钱/亏钱效应处于冰点/高潮哪一档 | `sentiment_daily` |
| S3 | 主力博弈 | 主力合力 | 龙虎榜席位共识/分歧/可信度 | `main_force_daily` |
| S4 | 主线·龙头 | 板学寻龙 | 当天主线板块、龙头梯队、妖股、独狼 | `mainline_daily` + `leader_pool_daily` |
| S5 | 龙头买卖 | 龙头接力 | 龙/妖/独狼在分歧日/一致日怎么买卖 | `leader_trade_daily` |
| S6 | 趋势战法 | 趋势龙头 | 机构趋势牛股筛选（八大特征） | `trend_candidate_daily` |
| S7 | 炒作六因子 | 题材炒作 | 题材稀缺/想象/突发/确定/最小阻力，值不值得炒 | `theme_factor_daily` |
| S8 | 交易心法 | 纪律心法 | 个人交易纪律评分（主线/三因素/心态/风控/禁杠杆） | `trade_log` |

> 设计原则：S1~S7 是「市场客观指标」计算层；S8 是「个人主观复盘」层（手动记交易日志，系统算纪律分）。
> S5 是**独立计算层**——它不直接算市场数据，而是综合 S2/S4 的状态 + 龙头定位，给出买卖建议（分析产出，非自动交易指令）。

## 2. 产品化目标

把书里「看完盘在脑子里过一遍」的流程，变成：

1. **可计算**：每个 skill 有确定算法 + 可调参数，给定交易日 T 的数据，产出同一套指标。
2. **可追溯**：计算层结果落库（ReplacingMergeTree，幂等重算），任意历史日可回看。
3. **可可视化**：前端按模块（总览/主线/情绪/趋势/题材/交易日志）呈现，支持按日期切换复盘。
4. **可自愈**：启动自动跑最新交易日；某 skill 落库为空自动重算；参数集中可调。

### 5.2 双数据源（核心架构约束）

| 数据源 | 类型 | 角色 | 是否参与分析 |
|--------|------|------|------------|
| `og` (openGauss, `@Primary`) | PostgreSQL 协议 | 仅存 `replay_calc_task`（分布式任务行记录） | 否 |
| `ch` (ClickHouse `crawler`) | 列式分析库 | **业务/分析数据「全部」走 CK**（读原始层 + 写计算层） | 是 |

- CK 不支持事务 → 写入强制 `auto-commit`；JDBC 批量 INSERT 曾**静默丢数**，已根治为**裸 HTTP 直写**（见 §7.1）。
- CK 读必须带 `FINAL`（ReplacingMergeTree 取最新版本）；RMT 表 `_ver = DateTime MATERIALIZED now()`，纯 INSERT 幂等。
- Windows CK 偶发 NAT 掐连接 → Hikari `max-lifetime: 300000`(5min) + `keepalive: 30000` + `connection-test-query: SELECT 1`（见 §7.2）。

### 5.3 配置要点（`application.yml`）

- `server.port: 8090`
- `replay.calc.on-startup: true` —— 启动对最新交易日跑一轮（端到端验证）。
- `replay.sentiment / mainline / leader / theme` —— **阈值集中管理**，按市场风格调参（如冰点涨停≤30、主线 top-n=20、龙头每板 top-5、六因子等权 0.2）。
- `replay.task` —— 心跳 60s、单类型最大重试 3 次。

## 8. 关键工程机制

### 8.1 CkHttpWriter（裸 HTTP 直写，根治静默丢数）

- **根因**：Windows CK 上 JDBC 批量 INSERT 会**静默丢**（驱动返回成功、服务端未提交）；Mac 直连报 `Connection is closed`。
- **方案**：所有计算层写入走 `service/CkHttpWriter.java` 裸 HTTP（`clickhouse-client` 协议）：
  - 每请求新建连接，VALUES 分块(100) + 6 次指数退避重试；
  - `count()` 用 `FINAL` 取真实行数校验；CK 23.8 不支持 URL `format=`，SQL 内 `FORMAT JSONEachRow`；
  - 被 `ReplayCalcJob.computeS1~S7` 调用（列清单硬编码常量，与 mapper XML 一致）。
- 读取仍走 MyBatis/JDBC（`safeStep`/`safeRead` 仅用于读，失败默认视为缺失→宁可重算不漏数）。

### 8.2 CkRetryInterceptor（瞬态重试）

- MyBatis 插件，挂 `ckSqlSessionFactory`，拦截 `SQLException` 含瞬态词（failed to respond / connection is closed / socket exception / connection reset / read timed out）。
- 重试 4 次，退避 0.5/1/2/4s + `softEvictConnections`；**仅拦 query**，写走 HTTP 不受影响。

### 8.3 RMT + FINAL 一致性

- 全部表（源+计算层）均为 `ReplacingMergeTree`，`_ver = DateTime MATERIALIZED now()`，纯 INSERT 幂等。
- 读路径 RMT 表必须 `FINAL`；后台合并延迟不影响查询结果正确性。

### 8.4 双数据源 & Hikari 调优

- `DataSourceConfig` 手动配两个 `SqlSessionFactory`（og `@Primary` / ch），排除 MybatisAutoConfiguration 自动配置。
- CK Hikari：`max-lifetime: 300000`（5min 强制重建，规避 NAT 掐长空闲连接）、`keepalive: 30000`、`connection-test-query: SELECT 1`、`idle-timeout: 60000`。
- 压测验证：15 轮×4 接口 27/80 失败 → 调优后 0/60 失败。

### 8.5 参数化阈值（ReplayProperties）

- `application.yml` 的 `replay.*` 集中所有阈值（情绪分档、主线权重、龙头 top-n、六因子权重），改 yml 即调参，无需改代码。

### 8.6 启动自跑 + recalc 自愈

- `ReplayStartupRunner` → 启动对最新交易日跑 `ReplayCalcJob.run()`。
- `verifyAndRepair`：逐表 `count==0` 则重跑该 skill，循环 5 轮；`recalcMainline` 同法。
- `AdminController`：`/admin/recalc`（全量自愈）、`/admin/recalc-mainline?date=`（只重算 S4）、`/admin/derive-concepts`（手动刷新概念）。

### 8.7 概念派生惰性化

- `concept` 已有则跳过；手动 `POST /admin/derive-concepts` 刷新。`ConceptClassifier` 过滤伪概念。
