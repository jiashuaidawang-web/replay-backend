## 二、缺陷清单（按严重级）

### 🔴 P1 — 阻断级（功能不可用）

#### BUG-1：S8 交易日志 / 纪律评分 全部 500（OG 连接不可用）
- **复现路径**：`GET /api/v1/trade-log`、`GET /api/v1/trade-log/discipline`、`POST /api/v1/trade-log`（带任意参数）→ 全部 500
- **复现证据**（2026-08-19 实测）：
  ```
  GET /api/v1/trade-log          -> 500 Internal Server Error
  GET /api/v1/trade-log/discipline -> 500 Internal Server Error
  GET /api/v1/trade-log?date=2026-08-14 -> 500 Internal Server Error
  ```
- **根因**：S8 trade_log 表建在 **openGauss（@Primary 数据源）**。Mac 端后端直连 Windows openGauss(100.97.74.45:5432) 时 `HikariPool-2` 初始化即失败：`Connection reset` / `Read timed out`（SSL enable 阶段 SocketTimeoutException）。服务端日志栈：`HikariPool-2 - Exception during pool initialization` → `org.postgresql.util.PSQLException: 尝试连线已失败`。**非 Service 层 bug**（TradeLogService/DisciplineCalculator 逻辑正常），是网络/驱动层问题。
- **影响**：前端 ⑬ 交易日志页、⑭ 纪律评分页 全部不可用；S8 技能整体无法验收。
- **修复建议（按优先级）**：
  1. **推荐：trade_log 迁到 ClickHouse**（crawler 库），与其余 8 张计算层表同源，彻底摆脱对 OG 的运行时依赖（OG 仅保留 replay_calc_task 即可）；写路径复用 `CkHttpWriter` 裸 HTTP 直写。
  2. 或：OG 连接池加重试 + 降级（OG 不可用时返回 503 + 友好提示，而非 500）。
  3. 或：确认 Windows 主战场 5432 端口连通性；若 Windows 本机跑后端则不受影响（但 Mac 开发/验收环境不可用是现实问题）。

### 🟠 P2 — 严重级（错误语义 / 偶发不可用）

#### BUG-2：sentiment 无数据日期返回 200 空 body（前端 `res.json()` 会崩）
- **复现路径**：`GET /api/v1/sentiment?date=2026-09-01`（未来交易日）→ **200 但 body 长度 0**
- **根因**：SentimentController 查询无数据时返回空 body 但未调整状态码。
- **影响**：前端 `res.json()` 解析空 body 抛 JSON 解析异常 → 渲染失败（被 catch 兜底为空白，用户看到"无数据"但无提示区分）。
- **修复建议**：无数据时返回 `204 No Content`，或返回 `{"tradeDate":..., "data":null}` 结构化空对象；前端 `res.json()` 前先判断 `res.status === 204`。

#### BUG-3：overview 无数据日期返回 200 但全 null（误导性"假数据"）
- **复现路径**：`GET /api/v1/overview?date=2026-09-01` → 200，返回 `{"tradeDate":"2026-09-01","fourDim":{"tech":null,...,"composite":null},"cycle":{"phase":null,...},...}` 全 null
- **影响**：前端拿到 tradeDate 非空，可能渲染"四维雷达全空 + 周期全空"的假看板，用户误以为系统坏了；且与列表接口（空数组）语义不一致。
- **修复建议**：统一"无数据日期"语义——overview 返回 204 或 `{available:false}`；前端对全 null 渲染"该日无数据，请选择其他日期"。

#### BUG-4：API 读路径无重试 → Windows CK 抖动触发偶发 500
- **复现路径**：对 `leaders` / `leader/trade-idea` 连续请求 3 轮，实测 **1 轮返回 500**（`BoardBasicMapper` 500 个 IN 参数查询命中 `BatchUpdateException: The target server failed to respond`）。top=500 时 `CommonService.boardNameMap` 产生 500 个 IN 查询，命中 CK 网络抖动即 500。
- **根因**：`safeStep`（5 次退避重试 + softEvictConnections）只用于**计算层读取**（ReplayCalcJob）；**API 读路径**（Service → Mapper）没有重试包装。
- **影响**：前端偶发"加载失败"，用户刷新即恢复，但体验不稳定；大盘股数增多时（top 拉满）概率更高。
- **修复建议**：给 API 读路径包一层 `safeRead` 重试（复用计算层的瞬态重试 + 清池逻辑）；`boardNameMap` 改为按 `IN (...)` 分批（≤200/批）或改用 JOIN 一次性查出。

#### BUG-5：主战场核对（08-17 源缺日优雅降级已确认，无需修复）
- **说明**：08-17（周一）源表 `limit_up_pool` 当日 0 行（爬虫漏抓）→ mainline/leaders/trade-idea 返回空数组（优雅降级 ✓）；sentiment 返回 `{thermal:10, regime:"冰点"}` 为计算产物非缺陷；overview 正常。**此项为数据问题非代码问题，需补爬虫后重算**。

### 🟡 P3 — 一般级（体验 / 防御性）

| # | 缺陷 | 复现 | 影响 | 建议 |
|---|---|---|---|---|
| 1 | 非法日期 400 无友好提示 | `GET /mainline?date=abc` / `?date=2026-13-99` → 400，body 为 Spring 默认 JSON，无中文提示 | 调用方/用户不明确错误原因 | 全局异常处理器 `@ExceptionHandler(MethodArgumentTypeMismatchException.class)` 返回 `{code:400, message:"日期格式应为 yyyy-MM-dd"}` |
| 2 | 超长参数 400 | `?date=<100位乱串>` → 400（Spring 默认） | 同上 | 同上统一处理 |
| 3 | datePicker 无 min/max | 前端 `datePicker` 无 `min`/`max` 限制，可选未来/周末日期 → 触发空态 | 用户困惑"为什么没数据" | 前端给 datePicker 设 `min=trade_calendar 最早交易日`、`max=最近交易日`；或后端 `resolveDate` 对未来日期自动回退到最新交易日 |

| 5 | `fund-flow/board` `orderBy=abc` 静默 200 | `?orderBy=abc&top=10` → 200 返回默认排序结果 | 参数错误被静默忽略，调用方无感知 | Controller 层校验 `orderBy ∈ {main_net, big_net, super_big, ...}`，非法值 400 |
| 6 | `top` 无上限 | `?top=5000` 可用 → 触发 CK 大批量 IN 查询，放大 BUG-4 抖动概率 | 性能风险 + 偶发 500 | `top` 限制 `≤200`，超限截断或 400 |

## 六、缺陷修复记录（2026-08-19 当日完成，全部回归通过）

> 按 P1 → P2 → P3 顺序修复并重启回归，**最终 15/15 用例 PASS + 60 请求压测 0 失败**。

### 6.1 P1 BUG-1：S8 trade_log 迁 CK（已修复 ✅）

- **方案**：trade_log 从 openGauss 迁到 ClickHouse（crawler 库），彻底摆脱 Mac→Windows OG 的 Connection reset。
- **改动**：
  - CK 建 RMT 表 `crawler.trade_log`（ReplacingMergeTree(_ver)，ORDER BY (trade_date, ts_code, id)）；
  - 新增 `TradeLogCk` 实体 + `TradeLogCkMapper`（ck 包）+ `TradeLogCkMapper.xml`；
  - `TradeLogService` 改造：写路径复用 **CkHttpWriter**（裸 HTTP 直写，与计算层同机制），读路径走 CK Mapper；id 改为 UUID String（原 Long hashCode hack 移除）；
  - `TradeLogVO.id` 类型 Long → String。
- **验证**：GET /trade-log、GET /trade-log/discipline、POST /trade-log（写入+读回）全部 200。

### 6.2 P2 BUG-2/3：统一"无数据日期"语义（已修复 ✅）

- **方案**：
  - `CommonService.resolveDate`：请求为空→最新交易日；**未来日期→回退最新交易日**（消除各接口未来日期行为不一致）；
  - `sentiment`：无数据→**204 No Content**（原 200 空 body）；
  - `overview`：四维+情绪+主线全无→**204**（原 200 全 null 假看板）；部分有→200 结构化对象；
  - 前端 `apiGet`：204 → 返回 null；`renderOverviewTiming/Mainline` 加 null 空态；datePicker 动态设 min(2024-01-01)/max(最新交易日)。
- **验证**：未来日期→回退 200 有数据；周六 08-15→204；正常日→200。

### 6.3 P2 BUG-4：API 读路径重试 + boardNameMap 分批（已修复 ✅）

- **方案**：
  - 新增 `CkRetryInterceptor`（MyBatis 插件，显式挂 ckSqlSessionFactory）：只拦 Executor.query，cause 链含 SQLException 且消息命中瞬态关键词（failed to respond / connection is closed / reset / timed out 等）→ 重试 4 次（共 5 次尝试），退避 0.5s/1s/2s/4s，重试前 softEvict 连接池；
  - `CommonService.boardNameMap`：IN 分批 ≤200；
  - **根因修复（关键）**：Windows 端（NAT/防火墙）会静默断开长空闲连接，Hikari 无法感知→复用即 "Connection is closed"（裸 HTTP 每请求新建连接 100% 可用）。将 `ch.hikari.max-lifetime` 从 1800000ms（30min）缩短到 **300000ms（5min）** + `idle-timeout: 60000`，强制周期性重建连接。
- **验证**：fix3（30min 生命周期）15轮×4接口 27/80 失败（34%）；fix4（5min）15轮×4=60 请求 **0 失败**；10 轮×3 接口再测 0 失败。

### 6.4 P3-1/2/5/6：参数校验与友好错误（已修复 ✅）

- **方案**：
  - `GlobalExceptionHandler` 扩展：MethodArgumentTypeMismatch（date=abc → 400 `INVALID_PARAM` 带示例）、MissingServletRequestParameter、IllegalArgumentException、兜底 500（记日志）；
  - `FundFlowService.boardFlow`：orderBy 白名单（main_net/super_big/big_net），非法→400；top ≤0→10、>200→截断 200；
  - `resolveDate` 未来日期回退（见 6.2）。
- **验证**：date=abc→400 友好 JSON；orderBy=abc→400；top=999→200 截断。
